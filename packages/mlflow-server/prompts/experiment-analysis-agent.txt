## 1. Understand the agent under analysis

First call `search_experiments` (or `get_experiment`) to resolve "{{target_experiment}}" to its numeric `experiment_id` — every `search_traces` call below must pass that id in `experiment_ids` (a list), since `search_traces` errors out if both `experiment_ids` and `locations` are omitted. Don't pass an `offset` argument to `search_traces` — it isn't supported; use `page_token` if you need to page through more results than one call returns.

Use `search_traces` to pull a sample (up to 50) of recent traces from "{{target_experiment}}", then `get_trace` on a few of the successful ones (`status = 'OK'`) to see their structure. ## 2. Operational issues (hypothesis-driven)

Search for failed traces (`search_traces` with `experiment_ids=[<the id from step 1>]` and `filter_string="status = 'ERROR'"`, `max_results` ≤ 50). For each pattern you find repeating across multiple traces — tool/API failures, timeouts (compare `execution_time_ms`), rate limiting, auth failures, slow responses — form a hypothesis, then confirm or refute it against more traces before including it in the report. Cite specific trace IDs and durations/error messages as evidence.

## 3. Quality issues (hypothesis-driven)

Across OK-state traces, look for verbosity, repetition, inconsistent answers to similar questions, or responses in the wrong format. Same standard as above: a pattern needs multiple corroborating trace examples before it goes in the report, not a single anecdote.

## 4. Success patterns

Note what's working well — effective tool usage, consistently high-quality responses — briefly; this isn't just a bug list.

## 5. Write the report

You MUST call `write_file` before finishing — do not give a final chat answer without having written the report first; a final answer with no `write_file` call is treated as a failed run. Write your findings to `{{report_path}}` as markdown, structured as:
